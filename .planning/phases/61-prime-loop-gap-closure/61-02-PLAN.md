1. `ToolRegistry.runtime_bindings: dict[str, Any]`, empty by default (CREATED by loop unit).
   This plan consumes it: when heartbeat registration is enabled for a resolved job path, it
   reuses the bound `runtime_bindings['prime_heartbeat']` instance when its path matches the
   resolved `root/cron/jobs.json`, and only otherwise constructs a `HeartbeatRuntime` and
   publishes it at that key. At most one live runtime per registry per resolved path: no global
   singleton, no path-keyed cache, no second runtime for the same path, no parallel binding
   convention. Disabled registration publishes no binding and constructs no runtime (no threads
   when flags are off). Named sessions share this one authoritative registry-bound runtime.
   Committed tests in this plan exercise the real `ToolRegistry` binding surface and the real
   runtime; they use no registry doubles and no forwarding-echo assertions.
2. `HeartbeatRuntime(path)` public surface (THIS plan implements; loop glue consumes):
   `__init__(path, *, event_sink=None, clock=None, scheduler=None)`,
   `bind(name, runner, *, event_sink=None) -> None`,
   `unbind(name, *, runner=None, stop_if_empty=False) -> bool`, `start() -> list[dict]`, `stop(*, wait=True) -> None`,
   `schedule(session, prompt, *, interval_seconds, due_at=None) -> str`,
   `list_jobs() -> list[dict]`, `clear(job_id) -> dict`, `close() -> None`,
   plus `__enter__/__exit__` (exit closes) and a `bindings` snapshot property for glue introspection.
   `runner` shape: `runner(prompt: str) -> Any`, returning the actual run result/response.
   Per-binding sink: `bind` captures the runner and its sink together atomically under the state
   lock; each beat snapshots its own binding's pair before leaving the lock, so a second named
   session can never reroute the first session's error events. Rebind replaces the pair atomically;
   an in-flight beat keeps its snapshot. `unbind(name)` with `runner=None` detaches unconditionally
   and returns whether a binding existed; `unbind(name, runner=r)` detaches only when the stored
   runner is `r` (atomic expected-runner compare), so closing a replaced agent never detaches its
   replacement and never stops another live binding. The ctor `event_sink` is the service sink for
   undirected diagnostics only (beats with no binding at fire time): it never receives per-beat
   degradation owned by a named binding. Each sink call is guarded so a raising sink cannot kill
   the scheduler thread (the beat error is already recorded in job history).
   `clock`/`scheduler` are injectable seams defaulting to `time.time` and a fresh
   `BackgroundScheduler` (never shared with the generic `SchedulerService`).
3. `SessionLease.acquire(*, wait=False)` (THIS plan implements the primitive; loop unit consumes):
   keyword-only `wait`, default `False` preserves the existing fast-fail `RuntimeError`.
   `wait=True` blocks atomically until the lease is free, then takes it; `release()` wakes all
   waiters. The opt-in `wait` keyword on `run_conversation` / `OmegaPrimeAgent.run` belongs to
   the loop unit, not this plan.
4. Loop-glue responsibilities (loop unit, stated here so the seam is unambiguous): `OmegaPrimeAgent`
   owns `session_name` (default `'default'`); when a heartbeat binding exists it binds its live
   runner plus its redacted adaptor (`bind(session_name, self._heartbeat_runner,
   event_sink=adaptor)` or equivalent) before starting the runtime, and closing the last binding
   stops owned scheduling via conditional `unbind(session_name, runner=self._heartbeat_runner, stop_if_empty=True)` /
   `close`. This plan provides the primitives; it does not implement the glue.
</shared_interfaces>

<contract_conflicts>
Explicit resolutions for overlapping requirements. No silent reinterpretation.

- C1: LOOP-06 "capability failure degrades and continues" vs locked "do not swallow provider errors,
  KeyboardInterrupt, SystemExit, or ordinary policy/approval refusal". Resolution by domain:
  the BACKGROUND beat path (this plan) catches `Exception` from the bound runner, records it as
  the beat's structured error result plus a `prime_degraded` event routed to the owning binding's
  sink, and keeps the scheduler firing (loud, never silent). A non-JSON-serializable runner result
  is the same failure class: the beat outcome recorded is a structured `{"error": ...}` dict plus
  one redacted `prime_degraded` event, never a `repr()` marker persisted or emitted (jobs.json
  history bypasses the harness redaction path, so `repr()` would land unredacted internals on
  disk). `BaseException` (KeyboardInterrupt/SystemExit/CancelledError) always propagates and the
  in-flight guard is released. The FOREGROUND turn path (loop unit) keeps existing propagation for
  provider errors and policy/approval refusal; `guarded_hook` wraps only Prime hooks, never the
  provider core. A beat result shaped `{"error": ...}` is a recorded outcome, not a swallowed
  exception. No continuation-round cap is added here: the existing cumulative model-call cap and
  caller iteration budget stay authoritative.
- C2: Generic `SchedulerService` (prompt-only runner) vs heartbeat (session,prompt) routing.
  Resolution: reuse conventions, touch nothing. `apscheduler_backend.py` and `scheduler.py` are
  READ-ONLY neighbors: no helper extraction, no behavior edits. `HeartbeatRuntime` builds its own
  trigger arguments locally (valid interval heartbeat entries only; malformed
  rows are diagnosed and disarmed) following the same APScheduler conventions
  (`max_instances=1`, `coalesce=True`, `misfire_grace_time=None`,
  id-keyed entries), and reuses `JobStore` as-is. `test_apscheduler_backend.py` keeps passing
  unmodified because nothing it covers changes. `HEARTBEAT_KIND` filters every claim, read, and
  write: foreign cron rows in the shared jobs.json get no live entries and no writes; only
  heartbeat-kind rows are registered, fired, and finished.
- C3: `tick_heartbeats(store, now, session_runner)` existing signature vs runtime needs (lease wait,
  per-job in-flight guard, per-binding sink). Resolution: keep `tick_heartbeats` and `JobStore.tick`
  behavior unchanged for compatibility; the runtime implements its own fire path with identical claim
  semantics (claim-then-run-then-finish, `claimed_at`/`history` fields, `HISTORY_LIMIT` bound).
  No second job schema, no second store file. Never hold the state/JobStore lock while waiting for
  the session lease or running the runner callback: claim under the lock, release it, then wait and
  run, then re-acquire to finish.
- C4: `registry.dispatch` authority vs runtime schedule/clear. Resolution: tool handlers run INSIDE
  dispatch (called by it, under existing approval/policy gating) and delegate persistence plus
  scheduler-entry sync to the bound runtime. Runtime methods never bypass dispatch and never grant
  tools. Schemas, tool names, and `_WRITE_TOOLS` approval flags are unchanged. Same-path
  re-registration reuses the existing registry-bound runtime; named sessions share that one
  authoritative runtime, never a new multi-registry architecture.
</contract_conflicts>
