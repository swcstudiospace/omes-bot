# 63-08: Integration wiring

Two file-disjoint units written in parallel against the finished Wave 1 modules and the Phase 62 host.

## Unit A - the host (`remote.py`, `manifest.py`, `test_grokbot_integration.py`)

Compose the five Wave 1 modules into `create_sse_app` / `serve_sse` without changing any Phase 62 behavior when the new
options are left at their defaults (the Phase 62 tests must stay green).

1. New keyword arguments on `create_sse_app` and `serve_sse` (defaults in parentheses): `token_store_path` (None),
   `rate_limit` (120 requests/min per principal, 0 disables), `global_rate_limit` (0), `tool_rate_limit` (60 tool calls/min
   per principal, 0 disables), `auth_failure_limit` (10 failures per 60 s per client, 0 disables), `breaker_threshold` (5,
   0 disables), `breaker_cooldown` (30.0), `metrics_enabled` (True), `metrics_scope` ("read"), `log_format` ("text"),
   `session_idle_timeout` (1800.0), `max_sessions` (64), `approval_max_ttl` (86400.0), `clock` (None; injected clock for
   tests that is passed to the limiter/breaker/token store/approval log where they accept one).
2. Credentials: when `token_store_path` is given build `FileTokenStore(path)` (`omega_prime.grokbot.tokens`) and combine it with
   the env/file token store through `CompositeTokenStore`; auth is enabled when either exists. An unreadable token store makes
   `/readyz` report `token_store: degraded` (503) while auth still denies everyone.
3. Middleware, outermost first: `RequestContextMiddleware` -> `MetricsMiddleware` -> `AccessLogMiddleware` -> CORS (only when
   origins are configured) -> `AuthThrottleMiddleware` -> `AuthMiddleware` (its `on_failure` fans out to the audit
   `auth_failure` event, the metrics failure counter and `AuthFailureThrottle.record`) -> `RateLimitMiddleware`.
4. Tool-call interceptors in this order: `InFlightInterceptor`, `AuditInterceptor`, `MetricsInterceptor`, `ScopeInterceptor`,
   `ToolRateLimitInterceptor`, `ToolCircuitBreakerInterceptor`, then the caller's. Observers MUST precede every denying
   interceptor (`run_tool_call` stops at the first denial and runs `after` only for interceptors whose `before` ran); the
   integration test asserts that scope, rate-limit and breaker denials each appear in BOTH the audit log and
   `omega_tool_denials_total`. One shared `ToolGate`, one shared
   interceptor list, two `Server` instances (`transport="sse"` and `transport="http"`).
5. Routes: legacy `/sse` + `/messages` (unchanged), Streamable HTTP `/mcp` from `build_streamable_http` (its `lifespan()` is
   entered inside the app lifespan), `/metrics` (`metrics_endpoint`, scope from `metrics_scope`; absent when `metrics_enabled` is false),
   `/manifest.json` (scope `read`; the manifest of the EFFECTIVE settings, built once and cached; add an optional `runtime`
   argument to `generate_manifest` so it reuses the already built `Runtime` instead of building a second registry; the token
   value never appears; when auth is enabled `auth.type` is `bearer`), `/admin/approvals` from `approval_routes(...)` ONLY when
   authentication is enabled (with auth disabled these routes are not mounted: 404). `/healthz` and `/readyz` stay public and
   `/readyz` adds `token_store` and `streamable_http` checks. Public paths for `AuthMiddleware` stay exactly the two probes.
6. `app.state` gains `metrics`, `token_store`, `approval_log` (`runtime.approval_log`), `rate_limiter`, `breakers`.
   `serve_sse` calls `configure_logging(log_format)` (a process concern; `create_sse_app` never configures logging) and passes
   `session_idle_timeout`/`max_sessions` through.
7. `test_grokbot_integration.py` (real socket, same harness as `test_grokbot_e2e.py`; PyYAML not needed) proves Phase 63
   success criteria 1-4 end to end: an MCP client lists tools and calls one over BOTH `/mcp` and `/sse` with identical
   auth/origin behavior and audit records labelled `sse`/`http`; a token created with `tokens.create_token` works, is
   revoked (`revoke_token`) and the very next request is 401 without a restart; an expired token (injected clock) is 401; a
   `call`-scope token gets 403 on `/admin/approvals` and an admin token approves a gated tool with a TTL after which the
   call passes the gate, both audited with the approver principal and never the bot; a burst beyond `rate_limit` gets 429 with
   `Retry-After`; brute-force auth failures are throttled (429) and do not reach the tool; a tool that raises an
   infrastructure error `upstream_error: boom` (register it on `app.state.runtime.registry`, `no_roster=True`) opens the breaker
   after the threshold (`circuit_open` denial without running the tool) and recovers after the cooldown (injected clock);
   `/metrics` exposes request, tool-call, auth-failure and latency series and requires auth; responses carry `X-Request-Id`
   and `traceparent`, and the same request id is in the audit record; `--log-format json` style output is NDJSON with no
   token text; `/manifest.json` tool count equals `/healthz` `rostered_tools` and the tools listed over MCP.

### Integrator notes from Wave 1 (facts the Wave 1 units reported; use them)

- `AuthMiddleware.on_failure` events carry `client` which may be `None`: guard before `AuthFailureThrottle.record(client)`.
  `AuthThrottleMiddleware` sits BEFORE `AuthMiddleware`, `RateLimitMiddleware` AFTER it.
- A principal presenting someone else's `Mcp-Session-Id` on `/mcp` gets **404** (the SDK answers exactly as for an unknown
  session, which also hides that the session exists), not 403: `63-CONTEXT.md` said 403 and is wrong.
- `CompositeTokenStore` aggregates `degraded` / `degraded_reason` from its members; use them for the `/readyz` `token_store` check.
  `FileTokenStore` and `CompositeTokenStore` take `clock`: pass the app's injected `clock` through.
- `approval_routes(approval_log=runtime.approval_log, gated_tools=lambda: runtime.gated_tools, audit=tracer, ...)`; its audit
  writes run in a worker thread and a failed write only logs a warning. `revoke` of an expired approval is a 404.
- `is_infrastructure_failure` classifies `upstream_error`, handler exceptions (`ExceptionType: message`) and timeout/connection
  messages as infrastructure; the breaker interceptor creates a breaker only on a tool's first infrastructure failure (LRU 1024).
- The `429` bodies are `{"error": "rate_limited", "retry_after": n}` and `{"error": "too_many_auth_failures", "retry_after": n}`
  with a whole-second `Retry-After`.
- uvicorn's own access log must be OFF in the integrated host (`uvicorn.Config(access_log=False)`) because `AccessLogMiddleware`
  replaces it and never logs a query string; keep installing `StripQueryFromAccessLog` anyway as defense in depth.
- The Dockerfile's `CMD` (unit 63-07) passes `--log-format json` and `--token-file`; every flag it uses must exist after Unit B.

## Unit B - the CLI (`mcp_server.py` `main()` and argparse, `oneclick.py`, their tests)

1. `mcp_server.main()` gains: `--token-store PATH`, `--rate-limit N`, `--global-rate-limit N`, `--tool-rate-limit N`,
   `--auth-failure-limit N`, `--breaker-threshold N`, `--breaker-cooldown SECONDS`, `--no-metrics`, `--metrics-scope
   {read,call,admin}`, `--log-format {text,json}`, `--session-idle-timeout SECONDS`, `--max-sessions N`, `--approval-max-ttl
   SECONDS`; every one maps one-to-one onto the `serve_sse` keyword arguments of Unit A (same names as listed there;
   `--no-metrics` -> `metrics_enabled=False`, `--token-store` -> `token_store_path`). Negative numbers and non-positive
   session limits are usage errors (exit 2 with a one-line reason). Edit ONLY `main()` and the argparse block of
   `mcp_server.py`; keep `test_lint_types.py` guards intact.
2. `oneclick.py` forwards `--token-store` and `--log-format` to `serve_sse` and honors `--token-store` as an auth source (auth is enabled
   when a store is given); it exposes nothing else new (advanced tuning stays on `mcp_server`).
3. Tests: extend `test_grokbot_cli.py` (one case per flag mapping through the recorder for `serve_sse`, the usage errors) and
   `test_grokbot_oneclick.py` (token-store passthrough and bind-safety with a store).
