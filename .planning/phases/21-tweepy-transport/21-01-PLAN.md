# Plan 21-01: Tweepy transport adapter and dependency

## Goal

`XClient` speaks live X through `tweepy.Client` when constructed with the new
`TweepyTransport`, keeping the brokered bearer token, the five registry tools,
and the approval gates unchanged. The fake transport stays the default in
tests; the suite makes no live calls.

## Global Constraints

- Repository root is `/root/src/repos/Omes-Bot`. Commit only here.
- Do not modify `hermes-agent/` or `oh-my-pi/`. Do not import them at runtime.
- v4 adds real pip dependencies by user decision (2026-10-03); this plan adds
  `tweepy>=4.14` to `pyproject.toml` and a `pip install -e .` step to CI.
- No live X credentials in tests. No network in tests.
- Phases 1–20 tests still pass unmodified.
- A completion claim cites the pytest command and its exit code.

## Starting Point

`XClient` (`.planning/research/v3-x-api.md`, `omes/tools/x.py`) calls
`transport.get(url, headers, params)` / `transport.post(url, headers, body)`
and wraps non-XError failures with endpoint context. Verified against
tweepy 4.17.0 in `.venv`:

- `get_me(user_auth=False)` → `Response.data` dict
- `get_users_mentions(id, max_results=, pagination_token=, user_auth=False)` →
  `Response.data` list, `Response.meta` dict
- `get_tweet(id, user_auth=False)` → `Response.data` dict
- `create_tweet(text=, in_reply_to_tweet_id=, media_ids=, user_auth=False)` →
  `Response.data` dict
- `tweepy.Response(data=, meta=, errors=, includes=)` exposes `.data` / `.meta`
- Errors derive from `tweepy.TweepyException`

`tweepy.Client` is v2-only: media upload (`upload.twitter.com/1.1/...`) has no
tweepy method, so upload routes to a fallback raw transport. The bearer token
is extracted per call from the headers `XClient` already resolved, so broker
behavior is unchanged. OAuth1 user-context credentials are a follow-up; this
plan is bearer-only like v3.

## Task 1: transport adapter

### `omes/tools/x_tweepy.py` (new)

`TweepyTransport(make_client=None, fallback=None)` with the same
`get(url, headers, params)` / `post(url, headers, body)` shape as
`FakeTransport`/`HttpTransport`:

- `make_client(token)` builds the v2 client; default builds
  `tweepy.Client(bearer_token=token)`. Tests inject a stub factory — no
  network, no tweepy import required in the stub path beyond the module import.
- `get` routes `/2/users/me`, `/2/users/{id}/mentions`, `/2/tweets/{id}` to
  the matching client method with `user_auth=False`, returning
  `{"data": ..., "meta": ...}` plain dicts. Unknown paths go to `fallback`
  when present, else raise `XError`.
- `post` routes `/2/tweets` to `create_tweet`, mapping `reply` and `media`
  body keys to `in_reply_to_tweet_id` / `media_ids`. Upload-host posts go to
  `fallback`; without one, raise `XError` naming the missing media fallback.
- A missing or blank bearer in headers raises `XError` before any client call.
- `tweepy.TweepyException` becomes `XError` carrying the endpoint and the API
  message, matching what `XClient._wrap` produces for other transports.

### `omes/tests/test_x_tweepy.py` (new)

Stub factory recording calls, plus `XClient(TweepyTransport(...))` wired with
a static token (no broker needed — headers carry the token through):

- `me`, `mentions` (with `user_id`, `max_results`, `pagination_token`,
  `next_token` passthrough), `read_post`, `post` (reply + media ids),
  `thread` chaining — each asserting the stub method and arguments.
- Media upload bytes reach `fallback.post` at the upload URL.
- Stub raising `tweepy.TweepyException` surfaces as `XError` naming the endpoint.
- Unknown path without fallback raises `XError`; blank token raises `XError`.
- Default factory constructs a real `tweepy.Client` (construction only, no
  network) to prove the dependency wires.

### `pyproject.toml`, `.github/workflows/ci.yml`

- `dependencies = ["tweepy>=4.14"]`.
- CI installs the project (`pip install -e .`) before the test suite so the
  dependency is present; suite, evals, and assemble steps unchanged.
